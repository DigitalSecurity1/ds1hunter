### Release Packaging — All 3 Installers Bundled 71MB of Git History and Other Dev Debris

Asked to rebuild v1.0.5 for Linux, Windows, and macOS ahead of production release. Building the Linux package first surfaced a real packaging bug: the output was 201MB, roughly 15x the size of the equivalent pre-session build. Extracted and inspected the payload directly (without installing it - this machine runs the live production deployment at the same `/opt/ds1hunter` path the installer targets) and found the entire `.git/` directory (71MB) bundled inside, along with `.claude/`, `.pytest_cache/`, two large third-party `.deb` files (`apktool`, `jadx` - 72MB combined, confirmed via grep to be referenced by zero installer or runtime code, so purely accidental), stray `.log` files, and a dozen one-off `generate_*templates*.py` scripts used only during development to build the CVE template database.

Root cause: `make-release.sh`'s `rsync` exclude list had no rule for any of these - they were never a problem before because earlier builds simply predated some of these files existing in the repo. Confirmed `make-release-macos.sh` and `make-release-windows.sh` share the same copy-pasted exclude list and therefore the same bug. Fixed by adding `--exclude` rules for `.git/`, `.claude/`, `.pytest_cache/`, `*.deb`, `*.log`, and `generate_*.py` to all three build scripts identically.

Rebuilt all three release packages after the fix and verified each one directly (extracting the Linux/macOS `.run` payloads and the Windows `.ps1`'s embedded ZIP, without installing any of them): all three now build clean at 13-22MB, zero bloat entries present, and each contains every fix from this session (Think Mode tech-stack detection, the intercept proxy header-case-sensitivity and chunked-body fixes, the four scan-proxy/Tor routing gaps plus `mobile_pentest.py`'s three, and the Cloud Storage Bucket Scan opt-in gate). Also re-confirmed, while in the installer scripts, that two previously-diagnosed platform-specific fixes are intact: the Windows-specific OOB DNS server startup bug (`SelectorEventLoop` on `win32`, always-signal-readiness) that was the likely cause of v1.0.4 failing to run on Windows, and macOS's Homebrew-must-not-run-as-root fix (`brew_cmd()` wrapper). All three installer scripts pass their respective syntax validators (`bash -n` for the two `.sh` installers, PowerShell's own `Parser.ParseFile` for `install-windows.ps1`).

Not verified: an actual install run on real Windows or macOS hardware - only available for this session is a Linux dev machine, so the Windows/macOS installers are confirmed correct by direct code/package inspection and syntax validation, not by execution. The Linux package was similarly not installed end-to-end during this session, specifically because doing so would overwrite the live production deployment at `/opt/ds1hunter` running on this same machine - deferred pending confirmation from whoever needs to sign off on that install window.

### Windows Installer — Real-Hardware Test Caught an Extraction Crash the Linux-Only Verification Above Missed

A user actually ran the v1.0.5 Windows package on real hardware (Windows PowerShell 5.1) and hit an immediate failure: `Remove-Item : Cannot find path '...\ds1hunter-1.0.5\install-windows.ps1' because it does not exist`, thrown from inside Microsoft's own `Microsoft.PowerShell.Archive.psm1:411` during `Expand-Archive -Force`'s internal cleanup - not from any DS1 Hunter script code. This is exactly the gap the paragraph above already flagged: syntax validation and package inspection from Linux couldn't have caught a failure inside Windows' own archive-extraction implementation.

Ruled out the obvious suspects first by direct inspection of the actual shipped ZIP payload (10,703 entries): `install-windows.ps1` genuinely present at the expected path, no case-insensitive filename collisions (the zip was built on a case-sensitive Linux filesystem, extracted onto Windows' case-insensitive one - a common source of exactly this class of bug, but not the one here), no path exceeding Windows' 260-character `MAX_PATH` limit (longest was 177 characters), zip integrity clean (`testzip()` returned no errors). Root cause was 8 filenames in `core/templates/` (the nuclei-style CVE/traversal template set) containing a literal `:` - e.g. `traversal-qparam-file-C:-Windows-win-ini.yaml`, encoding the traversal target path `C:/Windows/win.ini` directly into the filename. A bare colon is legal on Linux/ext4 (where these were authored and zipped) but is reserved on Windows/NTFS as the Alternate Data Stream separator; `Expand-Archive` silently mis-extracts an entry with one, which then desyncs its own internal "what did I just extract" bookkeeping and throws the `ItemNotFoundException` above during cleanup.

Renamed all 8 files to drop the colon (`traversal-qparam-file-C-Windows-win-ini.yaml`), updating each template's internal `id:` field to match for consistency. Confirmed safe: `template_scanner.py`'s `load_templates()` globs `*.yaml` in the directory and takes each template's `id` from its YAML content, not its filename - nothing anywhere references these 8 by their old names. Also added a build-time guard to `make-release-windows.sh` (`find "$PAYLOAD" -name '*[<>:"|?*]*'`, run right before the ZIP is created) that fails the build loudly if any Windows-illegal filename character (`< > : " | ? *`) slips into the payload again, from any source, rather than shipping a package that only breaks on the target OS. This bug is Windows-packaging-specific only - `core/templates/` on the Linux production deployment at `/opt/ds1hunter` was never affected, since colons are legal there.

Rebuilt `dist/ds1hunter-CE-v1.0.5-windows.ps1` (22M) with the fix; the new build-time guard reported zero illegal filenames, and direct inspection of the rebuilt package's embedded ZIP confirms all 10,703 entries are now free of `< > : " | ? *`. Not yet re-verified on real Windows hardware - the original failure was only caught because a user tested on an actual machine, and that remains the only way to be certain `Expand-Archive` now completes cleanly end-to-end.

### Windows Installer — Extraction Fix Confirmed on Real Hardware; Follow-Up Login Failure on Windows 10 Home

The colon-filename fix above was re-tested on real hardware: extraction and install now complete successfully on both a Windows 10 Pro VM and a Windows 10 Home ("family") VM. Pro logged in fine with the generated credentials; Home rejected them with "Invalid credentials" despite the install reporting full success (services started, HTTPS login page reachable) - meaning the request pipeline itself was healthy, but the password typed/pasted at login didn't match what got stored during install.

Root cause not reproducible from this environment (no real Windows Home hardware available here), but two genuine gaps were found by re-reading `install-windows.ps1`'s credential path and fixed defensively regardless of which one actually caused this specific case:

1. `$SECRET_KEY`/`$ADMIN_PASS`/`$ADMIN_URL_TOKEN` were each captured directly from a `python -c` subprocess's stdout with no defense against stray output (a first-run interpreter banner, a deprecation warning) landing in the same capture and silently corrupting the value. Now takes only the last non-blank line of each call's output, and the install hard-fails immediately if the resulting password isn't exactly 24 characters, rather than silently carrying a corrupted value forward.
2. The admin-creation step declared success as soon as `create_superuser`/`set_password` returned, with nothing to catch a value that got created correctly but doesn't actually authenticate. Added an immediate self-check right after creation - `django.contrib.auth.authenticate(username='admin', password=pwd)` - that fails the install loudly if it doesn't come back with a valid user, turning a silent bad-credential into a clear install-time error with a diagnosable cause instead of a confusing failure at the user's first login, hours or days later.

Also added a plain, unpadded, single-line copy of the password below the bordered summary box - the boxed version pads every line with trailing spaces to align the box border, which is easy to over-select by a character or two in a small/low-resolution window (exactly the setup in this report: a VirtualBox VM shown in a phone photo) and silently break the copy-paste without any visible sign of a problem.

Linux and macOS installers intentionally left untouched - this class of bug is specific to `install-windows.ps1`'s credential-generation path, and there's no reproduced evidence either platform is affected. `install-windows.ps1` re-validated with PowerShell's own parser and a full extraction dry-run (marker detection, base64 decode, `Expand-Archive`, inner-script parse) after the change; rebuilt `dist/ds1hunter-CE-v1.0.5-windows.ps1` and re-uploaded to both the GitHub release and the website. Still pending: re-test on the same Windows 10 Home VM that hit the original failure, since that remains the only way to confirm this specific fix actually resolves it there.

### Windows Installer — Three More Real-Hardware Findings: AV Block, Slow Extraction, Boot-Time UI/API Race

Retesting the fixes above surfaced three more issues, reported together from real VM testing (a Windows 10 Pro VM and a Windows 10 Home/"family" VM, both in VirtualBox): (1) the Pro VM, which had installed cleanly before, now failed partway through with Windows' own real-time-protection message - "Installation failed: Operation did not complete successfully because the file contains a virus or potentially unwanted software" - during Step 2's file copy; (2) the archive-extraction step ("please wait...") was reported as taking a long time; (3) on the Home VM, the app sometimes didn't work right after a Windows restart until retried, and separately, Edge showed a black/blank page while Firefox loaded the same install fine.

Fixed the two issues with a clear, reproducible mechanism:

**AV block during file copy.** `install-windows.ps1` already adds a Windows Defender exclusion for the install directory - but only at Step 10, after Step 2 has already copied every payload file into that same directory unprotected. A pentesting tool's bundled payloads/signatures are exactly the kind of content real-time protection flags, and Defender's cloud-delivered verdicts aren't fully deterministic run to run, which is consistent with this passing before and failing now with no code change in between. Moved the exclusion to run immediately after the admin/Windows-version checks, before any file touches `$INSTALL_DIR`, and added a second best-effort exclusion for the self-extractor's own temp directory in `make-release-windows.sh`'s embedded extraction header, since that's the very first place payload files land on disk.

**Slow extraction.** `Expand-Archive`'s PowerShell cmdlet wrapper has real per-entry overhead that adds up across an archive with 10,703 entries. Replaced it with a direct call to .NET's `[System.IO.Compression.ZipFile]::ExtractToDirectory()` - same ZIP format, no cmdlet layer in between. This also sidesteps the entire class of bug the earlier colon-filename crash came from (Microsoft's own `Microsoft.PowerShell.Archive.psm1` cmdlet wrapper, not the underlying .NET compression API, was where that bug lived), rather than just working around this one instance of it.

For the boot-time race, found one genuine, fixable gap while re-reading the service-startup path: NSSM's `DependOnService DS1HunterAPI` on the UI service only guarantees the API's *process* has launched before Windows starts the UI service - it doesn't wait for daphne to actually finish loading certs/Django and bind its HTTPS listener, which takes a few seconds longer than the UI's lightweight static file server needs to come up. A user (or auto-launched browser) hitting the UI in that window gets a page whose first API call fails. Added a readiness wait to `start-ui.ps1` (polls `127.0.0.1:$API_PORT` via a raw TCP connect, up to 60s) before it starts serving - the UI service now simply won't accept connections until the API is confirmed reachable, on every service start, not just the initial install.

The Edge-black-page report is not fixed - no reproducible mechanism was found from source alone. The certificate trust path already handles Chromium's known requirements specifically (IP SANs for 127.0.0.1, `LocalMachine\Root` store so it's trusted machine-wide, not per-user) per an existing comment in the script, and a black/blank page (rather than a certificate-warning interstitial) doesn't match a trust failure anyway - it's more consistent with either a JS runtime error on load or a Chromium GPU-compositing issue specific to running inside VirtualBox without full 3D acceleration, which is a known category of problem unrelated to any specific website. Diagnosing this for real needs the Edge DevTools console output from the actual failing VM, which wasn't available here.

Both fixes validated the same way as prior Windows changes: PowerShell's own parser against both the outer self-extractor and inner `install-windows.ps1`, and a full extraction dry-run confirming the new `ZipFile.ExtractToDirectory()` path still produces a working, discoverable `install-windows.ps1` (10,606 files, ~7s). Linux/macOS installers untouched throughout - explicitly out of scope per this report. Rebuilt and re-uploaded `dist/ds1hunter-CE-v1.0.5-windows.ps1` to the GitHub release and the website. Still pending real-hardware re-test on both VMs.

### Windows Installer — "Invalid Credentials" on Windows Home Was Actually a Boot-Time Race, Mislabeled

Follow-up on the Windows Home VM: login failed with "Invalid credentials" on the very first attempt after starting the app in Firefox, then succeeded with the *same* password after simply closing and reopening the browser and trying again - nothing else changed in between. That pattern doesn't fit a real credential mismatch (which wouldn't spontaneously start working), and the Pro VM never showed it, consistent with a race that only bites on a slower/less-resourced machine.

Root cause was in two places, both ours: `start-ui.ps1`'s readiness wait (added earlier this same investigation) only confirmed the API's TCP port was open before serving the UI, not that Django itself was actually answering requests - a bare TCP connect can succeed the instant daphne binds its listening socket, before the ASGI/Django stack has finished its cold-start (the first request through the full middleware chain is measurably slower than steady-state). A login POST landing in that gap fails as a network/timeout error, not an auth error. But `frontend/src/pages/Login.js`'s submit handler had a bare `catch { toast.error('Invalid credentials...') }` with no distinction between "the server rejected these credentials" (`err.response` present, a real 401) and "the request never reached a server at all" (`err.response` absent - network error, timeout, connection refused). Both cases showed the identical message, so a transient not-ready-yet condition was indistinguishable from a genuinely wrong password.

Fixed both: `start-ui.ps1` now polls `https://127.0.0.1:$API_PORT/` with a real HTTPS GET (self-signed cert trust bypassed for this internal loopback check only) and waits for any response under 500, not just an open port - confirming the actual Django/ASGI pipeline is live, the same pipeline a login request travels through. `Login.js` now checks `err.response`: a real 401 still shows "Invalid credentials. Please try again."; a missing response shows "Can't reach the DS1 Hunter server yet. It may still be starting up - please wait a few seconds and try again." - an accurate message instead of a misleading one.

The frontend fix required a full `npm run build` rebuild (frontend source isn't tracked in git per the no-code-disclosure policy, so this doesn't show in the repo diff - it's bundled directly into the release package). Confirmed the new build's minified bundle contains the new message string before re-packaging. Both changes validated the same way as prior Windows fixes: PowerShell's parser against the outer and inner `.ps1` scripts, and a full extraction dry-run. Windows-only - Linux/macOS untouched, though the Login.js logic itself is shared frontend code that would apply equally there if those packages are ever rebuilt. Rebuilt and re-uploaded `dist/ds1hunter-CE-v1.0.5-windows.ps1` to the GitHub release and the website. Still pending real-hardware re-test on the Home VM that reported this.

### Sidebar Username/Logout Silently Missing on Login (All Platforms) - Stale Auth Effect

Reported independently of the Windows work above: after logging in, the username/avatar and Logout control at the bottom of the sidebar simply weren't there, on both a native Linux install and a Windows VM. A full page reload made them reappear with no other change. That pattern - works after a reload, not on first login - pointed at a mount-time-only effect, not anything platform-specific.

Root cause confirmed in `frontend/src/App.js`: the effect that fetches `/api/users/me/` and sets `user` ran once, on mount, gated on `[]`. On the login page, `token` is still null at that mount, so the effect takes its `else` branch and never fetches a profile. `login()` sets the token afterward, but the mount effect never re-runs to notice - `user` stays `null` for the rest of that session. The sidebar's username/Logout block is gated on `{user && ...}`, so it silently rendered nothing, with no error anywhere to point at. A reload "fixed" it only because that fresh mount already has the token from `localStorage` before the effect runs.

Fixed by extracting the profile fetch into a shared `fetchUser()` and calling it from both the mount effect (existing-token case, e.g. a reload) and directly from `login()` (fresh-login-within-session case) - rather than widening the effect's dependency array to `[token]`, which would have also re-fetched the profile on every silent JWT refresh (harmless but wasteful, since the refresh flow doesn't change who the user is).

This bug is in shared frontend source, not anything Windows-specific from the fixes above - confirmed via a live Django-shell test against the real production database that `UserProfileSerializer` itself serializes cleanly (ruling out a backend crash as the cause) before concluding it was a pure frontend effect-timing bug. Deployed immediately to the live `/opt/ds1hunter` instance (frontend bundle + `ds1hunter-ui` service reload only - no installer or backend service touched) and confirmed working there. Also rebuilt and re-validated all three release packages (Linux, macOS, Windows) with the fixed bundle, confirming each contains the identical corrected `main.*.js` and that Linux/macOS's `install-*.sh` scripts (unmodified by this fix) still pass `bash -n`. No installer script logic changed on any platform - only the bundled frontend content.

### Windows Installer — Firefox Certificate Trust Missed Real (Per-User) Firefox Installs

Live retest of the fixed login-message-clarity work above surfaced the real condition it was designed to surface clearly: on the Windows Home VM, the login page loaded over HTTPS showing "Not Secure" in the address bar, and login failed with "Can't reach the DS1 Hunter server yet" - a genuine certificate-trust gap, not a wrong password or a boot race. Traced to `install-windows.ps1`'s Firefox auto-trust step, which only checked `C:\Program Files\Mozilla Firefox` and the `(x86)` equivalent for `firefox.exe`. Modern Firefox installers default to a **per-user** install under `%LOCALAPPDATA%\Mozilla Firefox` unless "install for all users" is explicitly chosen during Firefox's own setup - an entirely normal, common install path this check never covered, so the `ImportEnterpriseRoots` policy silently never got written for that install, with nothing in the output to indicate it had been skipped.

Confirmed this is unrelated to the DS1 Hunter intercept-proxy's own MITM CA (`ProgramData\DS1Hunter\proxy_ca\`, generated by `core/proxy/ca.py`) - a completely separate certificate for a completely separate feature. The cert in question here (`certs\ds1hunter.crt`) is only ever the local web app's own TLS leaf certificate for `127.0.0.1:13000`/`:18000`.

Fixed detection two ways, both additive to the existing check rather than replacing it: added the per-user `%LOCALAPPDATA%\Mozilla Firefox` path directly, and added a lookup against Windows' own `HKLM:\...\App Paths\firefox.exe` registry key, which records wherever the installer actually placed `firefox.exe` regardless of which of these locations (or another one entirely) it used - more robust than enumerating guesses. The policy-writing step itself (`ImportEnterpriseRoots` via `distribution\policies.json`) is unchanged; it now just runs against every Firefox install actually found, instead of only the two hardcoded system-wide locations. Also rewrote the final summary's Firefox guidance to include the same reliable manual fallback Linux's installer has always pointed users to (`Authorities > Import > Trust this CA to identify websites`, with the exact certificate path), in case Firefox's own enterprise-policy support doesn't apply for some other reason (e.g. a build that ignores `distribution\policies.json` entirely) - previously the fallback only suggested visiting the API port once, which grants a weak per-origin exception (still shows "Not Secure", and doesn't cover the API's port separately from the UI's) rather than the genuine CA-level trust a proper import grants.

Re-validated the same way as every other Windows change this session: PowerShell's parser against both the outer self-extractor and the rebuilt inner `install-windows.ps1`, and a full extraction dry-run. Windows-only. Rebuilt and re-uploaded `dist/ds1hunter-CE-v1.0.5-windows.ps1` to the GitHub release and the website. Still pending real-hardware re-test on the Home VM that reported this, to confirm the per-user detection path was in fact the actual cause.

### Hunt — "Cloud Storage Bucket Scan" Ran on Every Hunt Regardless of the Off-by-Default Setting

User reported a real hunt against `dataprotect.ma` producing S3 bucket findings (`aws_s3_public_listing`, `aws_s3_bucket_exists`) despite never enabling the "Cloud Storage Bucket Scan" toggle - correctly suspecting the setting wasn't actually off by default. Confirmed directly against the database: `scan_cloud_storage=False` for that exact hunt, yet the findings were present.

This setting exists specifically because `CloudStorageScanner` guesses S3/GCS/Azure bucket names from the target hostname and probes them on AWS/GCS/Azure's own shared infrastructure - unlike every other check in Hunt, which stays within the target's own domain, a guessed bucket name existing doesn't confirm the target owns it, and probing third-party cloud infrastructure may fall outside an engagement's authorized scope. `core/hunter.py`'s own extended-checks section already gated this correctly (`if self.config.get("scan_cloud_storage"):`). The bug: `core/modules/auth_analyzer.py`'s `AuthorizationAnalyzer.run()` (Phase 2) had a second, completely independent call to the exact same `CloudStorageScanner` class, grouped in among several other unconditionally-run "OWASP gap" scanners with no gate at all - so cloud storage probing ran on literally every single hunt regardless of the setting, silently duplicating and bypassing the opt-in control at the same time.

Fixed by adding the identical `scan_cloud_storage` gate to this second call site. 2 new tests in `tests/auth_analyzer/test_cloud_storage_gate.py` (confirms the new gate is present immediately before the call, and that the original gate in `core/hunter.py` is still intact - this adds a second gate, it doesn't replace the first). Full 397-test suite passes.

### Scan Proxy / Tor — 4 Scanner Modules Silently Bypassed the Configured Proxy Entirely

Asked whether the Settings > Proxy configuration (including Tor) covers only Hunt and Active Scanner, or every scanner module. Audited every module in `core/modules/` for proxy usage. Most modules that looked like gaps at a first pass turned out to be false positives once traced to their actual callers: SAML/XPath Injection/WordPress/Vulnerable Libs/Second-Order/File Upload/Clickjacking all receive an already scan_proxy-configured `aiohttp` session or connector injected by Hunt, rather than importing `scan_proxy` themselves; JWT Analyzer makes zero network calls (pure offline token decode/tamper); Passive Scanner only analyses already-captured proxy history, never making a new request; `h2_desync.py` already correctly used `scan_proxy.open_raw_connection()`.

Four real gaps remained - all scanners that legitimately can't use a plain `aiohttp` session (they need either raw sockets for byte-level control, or `httpx` specifically for HTTP/2), which meant none of them ever went through `scan_proxy.make_connector()` the way every other scanner does:
- `core/modules/smuggling_scanner.py`'s raw TCP/TLS connection (HTTP request smuggling detection needs malformed request framing `aiohttp` won't send)
- `core/modules/active_scanner.py`'s own inline HTTP smuggling check, `_raw_http_send()` (same reason)
- `core/modules/race_condition.py`'s single-packet "last-byte sync" connections (needs to hold a request open mid-transmission across many concurrent sockets)
- `core/modules/grpc_scanner.py`, which uses `httpx` instead of `aiohttp` specifically because `aiohttp` has no HTTP/2 support

Fixed the first three by switching them to `scan_proxy.open_raw_connection()` - already built and used by `h2_desync.py` for exactly this "need raw sockets, still need proxying" case, so no new proxy-handling logic was needed there. `grpc_scanner.py` needed a new `scan_proxy.resolve_proxy_for_httpx()` helper - the `httpx`-client equivalent of `make_connector()`, with the identical policy: a loopback target always goes direct, an unreachable Tor/SOCKS5 proxy fails **closed** (raises `ConnectionError` rather than silently scanning direct - anonymity is the entire point of configuring Tor, so an erroring scan is a safer failure mode than a silently-deanonymized one), an unreachable non-Tor proxy falls back to direct. `httpx`'s SOCKS5 support needs the `socksio` package, added to `requirements.txt` (not `pyproject.toml`'s CLI dependency list, which doesn't include `httpx` either - gRPC scanning is a web-UI-only feature, not exposed through the standalone CLI).

10 new tests in `tests/api_scanners/test_proxy_routing_gaps.py` (the new helper's full policy: no-proxy/loopback/reachable/unreachable-Tor-fails-closed/unreachable-non-Tor-falls-back, plus source-level confirmation each of the four fixed call sites actually routes through `scan_proxy` now). Full 387-test suite passes. Live-verified all the way through real infrastructure before considering this done: `resolve_proxy_for_httpx()` against a real reachable Tor instance correctly returned the SOCKS5 URL, and an `httpx.AsyncClient` built with it successfully fetched `https://example.com/` over real HTTP/2 through Tor (200, 559 bytes); `open_raw_connection()` opened a real raw TLS socket through the same Tor instance and read back a genuine `HTTP/1.1 200 OK` from `example.com`; pointing the config at an unreachable Tor port confirmed the fail-closed `ConnectionError` fires instead of silently falling back to a direct, deanonymized connection.

Live-verifying `grpc_scanner.py`'s fix through the real production API surfaced two more pre-existing, unrelated gaps in the same module - both fixed alongside it since the feature was otherwise completely non-functional either way: (1) `/opt/ds1hunter/core/modules/grpc_scanner.py` only existed as a compiled `.pyc` in production, with no `.py` source ever deployed at all (the endpoint was reachable but every request would have hit an import error); (2) even with the source present, `h2` (the actual HTTP/2 protocol implementation `httpx`'s `http2=True` needs) was never installed on either the dev or production Python environment - `httpx` doesn't bundle it, only depends on it via an optional extra. Added `h2>=3,<5` to `requirements.txt` alongside `socksio` and deployed the missing source file. Re-verified with a real end-to-end request through the live API after both fixes: `POST /api/proxy/grpc-scan/` against `https://example.com` now completes cleanly (`error: null`, all 6 reflection/health/channelz probe paths checked and correctly returning "not present" for a non-gRPC target) instead of failing on the missing `h2` package.

A fifth gap turned up on a second pass, after `core/modules/mobile_pentest.py` had initially been cleared as "no network, static analysis only" - an assumption made without actually checking it. It makes three real, live outbound requests via the synchronous `requests` library, completely unproxied: `_verify_firebase_exposure` (`GET https://{host}/.json` against any Firebase Realtime Database host found in the APK), `_verify_cloud_storage_exposure` (`GET` against candidate S3/GCS/Azure Blob bucket URLs), and `_check_dependency_vulnerabilities` (`POST https://api.osv.dev/v1/querybatch`, cross-referencing bundled library versions against OSV.dev's CVE database). All three reveal the scanning machine's real IP to third-party infrastructure (Google/AWS/Microsoft/OSV) while verifying a target's exposure - exactly the kind of request Tor is meant to cover.

Fixed with a new `scan_proxy.resolve_proxy_for_requests()` helper - the `requests`-client equivalent of the other three `resolve_*`/`make_connector()` helpers, needing the already-installed `PySocks` package for SOCKS5/Tor (added to `requirements.txt` explicitly rather than relying on an undeclared transitive dependency). Unlike Active Scanner/gRPC Scanner/SSRF Tester - each a dedicated tool whose entire purpose is testing one target, where failing loudly on an unreachable Tor proxy is correct - these three checks are optional, best-effort, additive sub-checks inside a much larger static-analysis run. Letting a `ConnectionError` propagate up would fail the *entire* mobile pentest scan over one missing side-check, which is worse than simply skipping it. So each of the three call sites catches `ConnectionError` locally and skips just that check, matching each function's own pre-existing "best-effort, contributes nothing on failure" contract - Tor is never bypassed to keep the check running, but a Tor hiccup no longer takes the whole scan down with it.

8 new tests (`TestResolveProxyForRequests`, `TestMobilePentestUsesScanProxyForRequestsCalls` in `tests/api_scanners/test_proxy_routing_gaps.py`). Full 395-test suite passes.

### Intercept Proxy — Browsing a Target Through the Proxy Broke After the First Page ("Content Encoding Error")

User configured Firefox with the intercept proxy (CA cert installed, 127.0.0.1:8082) and reported that navigating a real target site worked for the first page or two, then further navigation intermittently failed with Firefox's "Content Encoding Error" - a response that looks structurally valid but whose body isn't a valid instance of whatever `Content-Encoding` it declared.

Root-caused with a live repro against the actual reported target: `curl -x http://127.0.0.1:8082 -k --compressed https://www.waitlesshub.com/` failed with curl's own decompression error, and the raw (undecompressed) response bytes were `6000\r\n<real gzip data>...` - a literal, un-stripped **HTTP chunk-size line** ("6000" = 24576 in hex) sitting directly in front of valid gzip data, still labelled `Content-Encoding: gzip`. That's not a truncation - the response was never dechunked at all.

Cause: `core/proxy/server.py`'s `_forward()` decided how to read the response body with `resp_headers.get("transfer-encoding", "")` - an **all-lowercase-only** dict lookup. `_parse_headers()` deliberately preserves each header's original on-the-wire casing (so pass-through headers look normal), and real servers essentially never send an all-lowercase `transfer-encoding` - nginx (and most everything else) sends `Transfer-Encoding`. The lookup missed every real-world response, `"chunked" in transfer_enc` was always `False`, and `_read_chunked()` was never invoked at all - execution fell through to the raw best-effort `read(_MAX_BODY)` fallback branch, which just returns whatever bytes are sitting on the socket, chunk framing included. A sibling lookup (`resp_headers.get("connection", "")`, used to detect an upstream-requested connection close) had the exact same shape and same miss.

Root cause #2, found via live testing after fixing #1 (stop still took 100+ seconds to take effect, confirmed via `journalctl` and the `live_data` endpoint showing the hunt stuck in `phase1, "Enumerating subdomains..."`): `tasks.py`'s real stop-checking (`check_pause_or_stop()`) only runs at ~13 coarse checkpoints between whole phases, invisible to sub-module internals like subdomain enumeration, which can run for minutes with zero internal stop-awareness. Root cause #3, found while implementing the #2 fix: even with `HuntStoppedError` now raised promptly, it would have been silently swallowed by `tasks.py`'s 6 pre-existing broad `except Exception:` per-phase handlers (which log a warning and continue to the next phase for any exception, not distinguishing a genuine sub-module failure from a deliberate stop) - completely neutering the #2 fix, since the hunt would just continue through all remaining phases after a stop request. ### Proxy Toolkit (Intercept, Intruder, Comparer, Repeater) — 7 Real Bugs Found and Fixed

Audited the full manual-testing toolkit end to end (`core/proxy/server.py`'s hand-rolled MITM engine, `ca.py`, `match_replace.py`, `scope.py`, `intruder.py`, and the Comparer/Repeater frontend + backend wiring) after being asked whether these tools actually work correctly and can help find real vulnerabilities. Most of the engineering underneath is genuinely solid — a real per-host dynamic TLS cert signer, a real LCS diff algorithm in Comparer, a real 4-mode (Sniper/Battering Ram/Pitchfork/Cluster Bomb) Intruder engine — but several concrete correctness bugs were undermining that work:

- **Editing a request's URL in Intercept had no effect on where it was sent.** `url` was updated for display only; the actual `_forward()` call kept using the pre-edit host/port/path computed before the edit. Fixed by re-deriving the forwarding target from the edited URL in both the plain-HTTP and HTTPS/MITM paths — carefully scoped to a per-request variable so an edit on one request over a keep-alive HTTPS tunnel doesn't leak into the next request on the same tunnel.
- **A Match & Replace rule that emptied a request body could hang the upstream server.** `Content-Length` was only recomputed when the (possibly rule-modified) body was non-empty; a rule reducing the body to nothing left the original, now-stale `Content-Length` in place, so the origin server would wait for bytes that were never coming. Now always resynced with the actual outgoing body.
- **Proxy Scope was entirely cosmetic.** `scope.is_in_scope()` had a full CRUD API and a frontend that explicitly claimed "exclude rules block it," but the live proxy engine in `server.py` never called it — every request was captured and eligible for interception regardless of scope rules. Wired scope checks into both the HTTP and HTTPS paths (out-of-scope traffic still forwards normally so browsing elsewhere keeps working, but is no longer logged to History or paused by Intercept) and corrected the UI copy, which previously overstated what the feature did.
- **Intruder silently mangled CRLF-injection payloads.** `parse_raw_request()` collapsed every `\r\n` to `\n` across the *entire* raw request text — including inside the body — before splitting into headers/body. A payload intentionally containing `\r\n` to test request splitting / header injection would have that exact sequence stripped before the request was ever sent. Fixed by only normalizing line endings in the header portion; the body now passes through with its bytes intact.
- **Comparer's "Load from proxy" only ever loaded the body, never headers, with no way to choose request vs. response.** One of Comparer's most common real-world uses — diffing response headers (`Set-Cookie`, auth headers, `Content-Length`, security headers) between two requests to spot user-enumeration or auth-bypass differences — was structurally impossible through the built-in picker. Added a Request/Response toggle and full raw-message formatting (status/request line + headers + body) so header-only differences now actually show up in the diff.
- **Repeater's "Replay" crashed with a 500 error on the single most common action: replaying a request without editing it first.** The frontend explicitly sends `"edited": null` for a plain replay; the backend called `edited.get(...)` directly with no None-guard, raising `AttributeError: 'NoneType' object has no attribute 'get'` every time. Reproduced directly. Fixed by defaulting `edited` to `{}` when the value is `None`, not just when the key is absent.
- **Editing a request in Repeater/Intercept and intentionally clearing the body (or headers) silently resent the original captured content instead.** The backend used Python's `or` to fall back to the captured entry's original value, which treats an intentionally-empty string/dict the same as "not provided." Reproduced directly with a cleared-body edit. Fixed by distinguishing "field omitted" from "field explicitly set to empty" using `is not None` checks instead of truthiness.

All fixes reproduced and verified before and after (URL-edit forwarding, Content-Length resync, scope enforcement, CRLF preservation, and both Repeater bugs each confirmed with a standalone repro script). Deployed to `core/proxy/server.py`, `core/proxy/intruder.py`, `web/apps/proxy/views.py`, and the frontend (`ComparerPage.js`, `ProxyPage.js`); verified with a full `manage.py check` and live endpoint checks post-deploy.

### Tor/Proxy Leak Fixed — Several Scan Paths Were Bypassing the Configured Proxy Entirely

Reported by a user who configured a Tor proxy in Settings and, watching the interface with EtherApe during a scan, never saw a Tor circuit form — meaning traffic wasn't actually going through Tor despite it being "on." That observation was correct. Audited every place the scanning engine opens a network connection and found the proxy setting was silently ignored in several of them.

- **Three Playwright/Chromium browser launches had zero proxy configuration** — `active_scanner.py`'s DOM-XSS headless check, `endpoint_discovery.py`'s headless crawl (part of Hunt's Phase 1, runs on *every* Hunt scan), and `verifier.py`'s DOM-XSS verifier. - **`scan_proxy.make_connector()` failed open for everything, including Tor.** If the configured proxy was unreachable at the moment of a request (e.g. Tor's SOCKS port not up yet during circuit bootstrap), it silently fell back to a direct, unproxied connection with nothing but a `logger.warning()` — meaning an entire scan's HTTP traffic could leak to the real network with no visible indication anything went wrong. - **Six aiohttp code paths built their own raw `TCPConnector`/`ClientSession` instead of going through `scan_proxy`, bypassing it completely regardless of settings**: `logic_engine.py`'s role-B/anonymous authorization-testing sessions (used by every BOLA/authz check that compares access across roles), `waf_identifier.py`'s three real-IP-discovery/baseline-fingerprint requests (ironically the module most likely to reveal the scanner's presence, since its whole job is finding origin infrastructure behind a WAF/CDN), `api_pentester.py`'s OpenAPI/Swagger spec fetcher, `active_scanner.py`'s anonymous IDOR-probe session, and `ai_llm_scanner.py`'s unauthenticated-access session. - **`h2_desync.py`'s HTTP/2 desync probes don't use aiohttp at all** — they open raw TCP/TLS sockets directly via `asyncio.open_connection()`, which has no concept of an HTTP proxy and can't be routed through `aiohttp_socks`. ### False-Positive Sweep, Round 4 — Cache Poisoning Redesigned, Systemic XSS Gap Fixed

Two were dangerously weak on their own: `RuntimeError|MemoryError|OverflowError` as bare exception-class-name words (no traceback context required - matches a blog post *mentioning* a RuntimeError), and `"stack"\s*:\s*"[^"]{30}` (matches any JSON API with an unrelated "stack" field - tech stack, a data structure, anything - with a 30+ char value). Added a baseline fetch/comparison and tightened both patterns to require the actual shape of a real disclosure (an `ExceptionName: message` format; a JSON stack value that actually contains `\n  at ` / `File "` trace lines) rather than bare word/key presence.
- **`PrototypePollutionScanner`** (`advanced_scanner.py`) - the most severe of the two: `_is_polluted()` had no baseline check, and checked bare substring containment against three words, one of which was **the literal word "admin"** against the *entire* response body and headers. Reproduced directly: a completely ordinary page with nothing more than an "Admin Panel" footer link - something most real websites have - triggered a false "prototype pollution reflected" finding. Also reproduced a second false-positive path: the check's other signal words ("polluted", "ds1hunter") are literal substrings of its own injected payloads, so a generic app merely echoing back an "invalid request: <payload>" error would also false-positive. Rewrote `_is_polluted()` to require the actual key:value shape a genuine pollution would produce (`"isAdmin":true`, `"polluted":"ds1hunter"` as a real JSON pair, not a bare word anywhere), added a baseline comparison, and added an echo guard that excludes matches sitting inside a verbatim copy of the submitted payload. Verified against all three cases (the reproduced false positive, the echo case, and a genuine pollution case) before shipping.

### Risk Score, Format-String False Positive, and PHP Deserialization False Positive - Found via a Real Scan

- User-reported, from a live Hunt scan showing 7 CRITICAL / 4 HIGH / 7 MEDIUM / 6 LOW findings but a **1.2/10** overall risk score: `_compile_report()`'s risk score formula (`core/hunter.py`) preferred the highest-scored *attack chain* outright whenever any chain existed at all, only falling back to the highest individual finding's CVSS score when zero chains existed. A single weak/low-confidence chain (this scan had exactly one) silently suppressed the true severity signal from every unrelated CRITICAL finding that never made it into that chain. Fixed to take the greater of both signals - chain score and standalone-finding CVSS - instead of preferring chain score unconditionally.
- **Format string injection false positive**: `_test_format_string_injection` (`logic_engine.py`) had no baseline comparison at all and matched on a single occurrence of `ffff[0-9a-fA-F]{4,}` or bare `0x[0-9a-fA-F]{6,}` anywhere in the response - patterns that appear routinely in ordinary page content (asset-bundle hashes, analytics/tracking IDs, session tokens) with zero relation to a real memory leak. Reproduced directly: a page containing nothing but a hashed JS bundle filename and a tracking ID triggered a false CRITICAL "format string injection" finding. Fixed by requiring a baseline-absent match, keeping rare/specific crash strings (`segfault`, `stack smashing`, etc.) as strong signals on their own, and replacing the weak single-hex-substring check with a requirement for 3+ pointer-shaped tokens in a row - the actual shape a real leak from the `"%p " * 10`-style payloads would produce, which ordinary page content essentially cannot produce by coincidence.
- **PHP deserialization false positive, more severe**: `_PHP_DESER_ERROR_RE` (`active_scanner.py`) included bare `O:\d+:"` / `a:\d+:{` as trigger patterns - which is exactly the PHP serialization syntax the injected payloads (`'O:8:"stdClass":0:{}'` etc.) are made of. Reproduced directly: a completely generic, non-PHP application that merely echoes an "invalid input: <value>" error back with the submitted parameter satisfies the old pattern and would have been flagged CRITICAL "PHP Object Injection," regardless of language or whether any deserialization ever happened. Fixed by requiring an actual PHP runtime error/warning string (`PHP Fatal error`, `unserialize(): `, etc.) instead of bare payload syntax; verified against both the false-positive case (now correctly not flagged) and two genuine PHP error strings (still correctly flagged).
- **Found the reason PHP deserialization findings could never show as confirmed, real or not**: the finding sets no `type` field and `verifier.py` had no title-based route for it either, so it fell to `_v_generic` - which doesn't even replay the payload, just re-fetches the URL and always reports "unconfirmed" at 0.20 confidence regardless of ground truth. Added a dedicated `_v_php_deser` verifier that replays the exact payload via the same vector (query param or Cookie) the original finding used, reusing `active_scanner.py`'s own (now-tightened) `_PHP_DESER_ERROR_RE` as the single source of truth.

### Pause/Resume — Fixed in Both Hunt and Active Scanner

- User-reported: pausing a scan, then resuming it, would show the scan as already finished - as if resume had fast-forwarded to completion. Traced to the actual root cause rather than guessing: in both tools, pause was implemented as "don't start the *next* chunk of work," not a real suspend, and the chunk size was too coarse for the check to matter in practice.
- **Hunt (`hunter.py`)**: the only place that ever checked the pause flag was `_wait_if_paused()`, called from inside the progress-callback wrapper - which fires roughly 10 times across an entire scan, at phase-transition boundaries only. The injection-testing phase alone runs 9 checks concurrently (SQLi, XSS, SSTI, CMDi, NoSQLi, XXE, two OOB checks, SSRF) with budgets up to 240 seconds; pausing mid-phase had zero effect until that whole batch finished on its own. `logic_engine.py` had no pause-awareness of its own at all. Same root problem, slightly better odds, in `auth_analyzer.py` (5 progress-callback checkpoints against 49 individual request sites).
- **Active Scanner**: better-built at the mechanism level (a real `threading.Event`, checked via `_check_pause()`) but only checked once per *endpoint*, before `_probe_endpoint()` starts - not within an endpoint's own probe set, which loops through SQLi/XSS/CMDi/traversal/etc. payloads sequentially under a 90-second per-endpoint timeout. Endpoints already in flight when pause was hit kept running for up to 90s regardless.
- Fixed both by adding a pause checkpoint to the actual per-request delay instead of the phase/endpoint boundary: `BusinessLogicEngine` and `AuthorizationAnalyzer` each gained a `pause_check` constructor param and a `_paced_sleep()` method that checks it before every rate-limited request; `hunter.py` wires `pause_check=self._wait_if_paused` into both. Bulk-replaced the request-pacing call at every site: 57 in `logic_engine.py`, 48 in `auth_analyzer.py` (leaving the one-off unrelated 0.1s wait in the security-question lockout check untouched), 51 in `active_scanner.py` via an equivalent module-level `_paced_sleep(sid, delay)`. Verified via AST analysis that every one of the 51 `active_scanner.py` sites has `sid` in scope (including one nested closure, safe via Python's normal closure capture) before touching any of them.
- **Caught a self-introduced bug during the fix, before it shipped**: the bulk replacement in `active_scanner.py` initially rewrote `_check_pause()`'s own internal poll-loop sleep into a call to the new `_paced_sleep()` - which itself calls `_check_pause()` - creating infinite recursion that would have hit every single time a pause was actually active (the one case that matters). Caught by rereading the diff immediately after the sed, not by testing later; reverted that one site back to a bare `asyncio.sleep`.
- Verified end-to-end, not just compiled: a live test with a real `threading.Event` confirmed `_paced_sleep()` actually blocks execution while paused and resumes cleanly once unset (elapsed time matched the unpause delay, not the short probe delay).

  - **BOLA/IDOR** (`bola_tester.py`): fell to generic because `_classify()` had no route for "BOLA/IDOR" titles at all. New `_v_bola` re-fetches the object with a bare, credential-free HTTP session — if it still returns data with zero authentication, that's unambiguous confirmation regardless of which identity the original scan used as its "attacker" (the original victim/attacker credential headers were never persisted into evidence, so an exact replay of the original test isn't possible; this is the strongest re-check available without that).
  - **Subdomain takeover** (`subdomain_takeover.py`): same missing route. New `_v_subdomain_takeover` re-resolves the CNAME and re-runs it through the *same* fingerprint table the scanner uses (imported directly, not reimplemented, so the two can't drift apart).
  - **Open redirect**: had a route, but the verifier itself was wrong for 3 of the module's 4 finding types. It hardcoded a `'https://evil.com'` probe and checked only the `Location` header for the literal string `'evil.com'` — but `open_redirect.py`'s actual payload is a scan-specific canary host, and its "to javascript:", "to Data URI", and "via Meta Refresh" finding types never produce that Location-header pattern at all (meta-refresh redirects live in the HTML body, not a header). Rewrote `_v_redirect` to replay the *actual* recorded `evidence['payload']`/`evidence['param']` and check the right thing per finding type (body-based meta-refresh parsing reused from `open_redirect._check_meta_refresh`, scheme-specific Location checks for the other three).
  - **Race condition** (`race_condition.py`): same missing-route problem, compounded by a second one underneath it — even after routing, no re-test was possible because the scanner never persisted the `method`/`body`/`concurrency` a burst replay needs, only the resulting statuses/lengths. Added those three fields to every finding's evidence (`_add_finding()` now takes them as parameters). New `_v_race_condition` re-fires the same concurrent burst and checks for the *same* anomaly class named in the finding's title (inconsistent statuses / auth-bypass-under-race / state inconsistency / duplicate numeric processing) — and honestly reports "not reproduced this round" rather than "false positive" when a race window simply doesn't fire on a single re-test, since that's a timing property of the bug, not evidence it doesn't exist.
- Not yet covered by the same fix: prototype pollution, Java deserialization, and GraphQL field-auth-bypass findings have the identical underlying problem (evidence doesn't persist enough of the original request to replay it) and still fall to the generic verifier. Flagged as a known follow-up rather than patched now, since each needs the same evidence-plumbing work race condition just got, done per-module.

### Fourth Template False-Positive Class — WAF/CDN Catch-All Pages, Found via a Real External Scan

- A Hunt scan against a real external target (behind Cloudflare) reported 261 CRITICAL findings, nearly all "confirmed" RCE/LFI CVEs — for dozens of mutually-exclusive CMS products (WordPress themes, Dolibarr, Emlog, AVideo, MetInfo, etc.) simultaneously, all on the same generic paths (`/index.php/`, `/php-cgi/php-cgi.exe/`, `/php-cgi/php-cgi.exe/login`). A single site cannot run 40+ unrelated CMS platforms at once — the detection logic was broken, not the target.
- Root cause: ~2,347 templates send **no exploit payload at all** — a bare GET/POST to a fixed candidate path — and match success on nothing but a generic OR'd word list (`"root"`, `"uid="`, `"error"`, etc.) appearing anywhere in whatever comes back. Confirmed live: the flagged path returned a Cloudflare bot-challenge page (`cf-mitigated: challenge`, HTTP 403) — the exact same response Cloudflare serves for any blocked path, regardless of which CVE template requested it, letting a generic word list coincidentally satisfy dozens of unrelated templates at once.
- The codebase already had the right tool for this — `_is_catch_all()` compares a response against a one-time baseline probe to a guaranteed-nonexistent path and flags near-identical status+body as a WAF/CDN catch-all — but it was gated behind an opt-in `differential_check`/`differential` flag that essentially none of these 2,347 templates ever set. Made the check **unconditional** for both template formats (legacy `requests[]` and `evidence_chain`) instead of trusting template authors to opt in. Verified: a synthetic WAF-identical response is now correctly suppressed, while a genuinely different response (real exploit-looking output, different status) still passes through untouched. This also covers the equivalent case on non-WAF'd targets, since a payload-less probe's response is entirely a function of how the server handles a nonexistent path either way — exactly what the baseline captures.

### Active Scanner Verification — Header-Based Findings Were Unverifiable

- A live Active Scan found 3 real candidate findings (SQL Injection, Time-Based, via the `User-Agent` header) that all stayed permanently "Unconfirmed" after running Verify. Root cause: `core/modules/verifier.py`'s re-test functions (`_v_sqli_error`, `_v_sqli_time`, `_v_xss_reflected`) only knew how to re-inject a payload into a URL query parameter (`evidence['param']`) — Active Scanner's header-injection checks (`_check_sqli_headers`, `_check_xss_headers`, etc.) record `evidence['header']` instead, so every one of these functions immediately returned "No parameter in evidence" without ever attempting a re-test, regardless of whether the underlying finding was real. This affected the entire header-injection detection category — the same class of vulnerability (SQLi/XSS via headers) that motivated `second_order.py`'s header-canary checks earlier this session.
- Fixed with a shared `_injection_point()`/`_apply_injection()` helper that re-derives whether the original finding used a URL parameter or an HTTP header and builds the re-test request accordingly, injecting into the header when that's what the evidence indicates. Applied to all three affected verifiers.
- Also fixed a related classifier bug found in the same investigation: Active Scanner titles this finding type `"(Time-Based)"`, but `_classify()` only matched the literal substring `"time blind"` — so every header-based time-SQLi finding was routed to the *error-based* re-tester (which checks for DB error text, not a timing delay) instead of the time-based one, meaning it could never confirm even a genuinely real time-based injection. `_classify()` now also matches `"time-based"`/`"time based"`.

### Template Matcher False Positives — Found via Live Testing

- A real Hunt scan against a live target (the first live-fire test this template library had received) surfaced dozens of nonsensical critical findings — an Apple iOS kernel CVE, a SCADA CVE, a WebLogic RCE — all flagged against a plain Django site. Root-caused to three related matcher patterns, none of which the earlier `confidence: low` exclusion caught because it trusts the template's *claimed* confidence label rather than inspecting what the matcher actually checks:
  1. **Status-only matchers** — a request-def whose entire evidence is `status: [200]` (or similar) with `matchers-condition: and`. 4,236 templates had at least one; 388 were mislabeled `confidence: medium`/`high`, so they were never excluded.
  2. **OR-shortcircuit** — `matchers-condition: or` combining a content-specific matcher with a bare status matcher. Under OR semantics, the status branch alone satisfies the whole thing (`any()` wins), making the specific matcher decorative. E.g. one template matched a literal `<script>alert(1)</script>` reflection **or** simply `status: 200` — meaning it fired on any 200 response. 2,399 templates affected.
  3. **Fingerprint-step-alone** — many templates use a two-step design (step 1: confirm the tech stack, step 2: the actual exploit probe), but `_run_template()` evaluates every request-def independently, so the fingerprint step can produce its own "confirmed critical CVE" finding purely because the target runs PHP/Apache/nginx — regardless of whether the real exploit step ever matched. 540 templates affected, all with *no* explicit `confidence` field, defaulting to `medium` via the severity fallback and therefore completely unprotected by the earlier filter.
- Fixed at the matcher level, not the label level: any request-def satisfiable by a bare status code or a ubiquitous platform name alone is now skipped before it's even requested. Verified impact: 1,979 templates go fully inert (1,785 already `confidence: low` — zero coverage cost; 194 genuinely newly suppressed, all previously-unprotected `confidence: None` templates whose *only* content was a tech-fingerprint check with no real exploit signal). Another 3,223 templates keep their legitimate exploit-probe request-def and lose only the parasitic false-positive one.
- **A fourth, deeper bug found on the next live re-scan**: `_match_single()`'s `type: word` matcher — the core primitive every template's word matching runs through, for both the legacy and evidence_chain formats — did plain Python substring containment (`word.lower() in text.lower()`) with no word-boundary awareness. Proven false positive: a D-Link firmware CVE template fired on `https://www.digitalsecurity1.com/` because its matcher word `"D-Link"` appeared as a raw substring inside `hprod-link`, a CSS class name on the site's own product page link — completely unrelated to running D-Link firmware. This is the same substring-matching bug class fixed in the offline template *generator* earlier this session (`\brds\b` matching inside "records", etc.), independently present in the live *scanning engine* itself, which had never been checked. Fixed with the same word-boundary approach: single-token words (start/end alphanumeric, e.g. `"D-Link"`, `"PHP"`) now match via `\b`-wrapped regex; words intentionally used as prefixes (e.g. `"ORA-"` matching `"ORA-01017"`) or multi-word phrases keep substring matching, since they already carry their own boundary and a prefix match is the correct, intended behavior for those. Applied to both the primary word/not-word matcher and the differential `baseline` matcher, which had the identical bug.

### Mobile Pentest — Critical Fix: Live UI Was Silently Hiding 100% of Static-Analysis Findings

### Mobile Pentest — Sessions Now Survive a Restart (DB-Backed Persistence)

Asked why a session "disappeared" - after the accuracy-pipeline fix above required a service restart, the user's in-progress session (and its history entry) vanished, and they asked directly: "no session saved? why?" Root cause: both Mobile Pentest session types (`core.modules.mobile_pentest`'s static upload-analysis sessions and `core.mobile_process_manager`'s "Analyze Device" dynamic sessions) have only ever lived in a plain in-process Python dict - by design, for thread-safe streaming updates during a scan - but with no durable backing store. Every one of the 35+ scanner modules in this codebase uses that same in-memory-dict pattern, so this wasn't a regression, but for Mobile Pentest specifically (large uploads, longer scans, a report the user may reference later) losing everything on every restart/crash was a real gap worth closing.

### Fixed: Real DNS Leak Bypassing the Tor/SOCKS5 Scan Proxy During Subdomain Enumeration

User reported live, direct-looking network traffic in a packet capture while running a Hunt scan with the Tor proxy toggle enabled and its "Tor Verified Exit IP" connection test passing - asked directly whether traffic was actually going through Tor. Deployed and restarted immediately at the user's request, interrupting their in-progress live hunt to close the leak rather than waiting.

### Fixed: Active Scanner Also Leaked a Direct TCP Connection (Not Just DNS) to the Real Target Before Every Tor-Proxied Scan

Immediately after fixing Hunt's subdomain-enumeration DNS leak, asked directly "how about the active scanner?" - audited `core/modules/active_scanner.py` (a separate, ~7,700-line module, not shared code with Hunt's discovery engine) the same way rather than assuming it was fine.

Found something worse than the DNS-only leak: `_scan()`'s pre-scan connectivity check opened a raw `socket.socket()` TCP connection directly to the real target's real IP - not just a DNS lookup - before the actual scan (and its correctly-configured Tor connector) ever started. This ran unconditionally, ahead of the `make_connector()`/`_via_proxy` setup, so a scan configured to run entirely through Tor still made one direct, unproxied TCP SYN from the tester's real IP straight to the target's server on every single run - handled by the target's own network stack, not just visible to a DNS resolver.

Fixed: when a proxy is configured (and the target isn't loopback, which a proxy can't route back to anyway), the pre-scan check now goes through the exact same proxied connector (`scan_proxy.make_connector()`) the real scan uses - a lightweight GET through that connector both confirms reachability and keeps DNS resolution + the TCP handshake on the proxy/Tor-exit side. Without a proxy configured, the original fast direct-socket check is unchanged. Swept the rest of the file for other raw-network primitives (`dns.resolver`, `requests.get`, `urllib.request`, `socket.gethostbyname`) - none found; the Playwright-based crawl path was already correctly passing `scan_proxy.playwright_proxy()` into the browser launch, so Chromium's own networking (including its DNS) was never a leak.

Verified live against the running service, the same way as the DNS fix: minted a fresh session against a real external target with the Tor proxy enabled, sampled `ss -tnp` on the daphne process through the pre-scan-check window and the rest of the run - every connection went to `127.0.0.1:9050`, and the session's own `proxy_status.bypass_count` stayed at 0 throughout, including the phase that used to leak.

### Hunt Now Shows Live Tor/Proxy Routing Status (Was Active-Scanner-Only)

User asked why Hunt had no equivalent of Active Scanner's live "Routing via Tor - no direct-connection fallback so far" indicator, right after the two proxy-leak fixes above - a fair question, since without it there's no way to see from the UI whether a Hunt scan is actually respecting the proxy setting while it runs.

Root cause: `core/hunter.py` already computed `scan_proxy.proxy_status_summary()` - but only once, into the final report dict returned after the whole hunt finishes. Active Scanner recomputes and re-sends it on every phase update instead, which is what its live indicator actually reads. Hunt's live progress payload (`_update_progress()`) never included it, so there was nothing for a live indicator to display during a run.

Added `proxy_status` to `_update_progress()`'s payload (same summary dict Active Scanner already uses: `configured`, `proxy_url`, `is_tor`, `bypass_count`, `warning`), threaded it through the WebSocket path (already a full passthrough, no change needed) and the REST polling fallback (`live_data` view, which cherry-picks specific fields and needed `proxy_status` added explicitly), and added the same indicator UI to `Hunts.js` that Active Scanner already has - green "routing via Tor" when clean, red bypass warning with a count if any request fell back to direct.

Also replaced the em dash in both the existing Active Scanner text and the new Hunt text with a plain hyphen, per request.

Verified live: started a fresh Hunt against a real target with Tor enabled, polled `live_data` while it was mid-scan (specifically during subdomain enumeration - the exact phase fixed earlier this session) and confirmed `proxy_status: {configured: true, is_tor: true, bypass_count: 0}` now comes back correctly, matching what the UI displays for Active Scanner.

### Fixed: HTTP Request Smuggling Scanner Flagged the Server Correctly Rejecting an Attack as a CRITICAL 9.8 Finding

User shared a real Hunt report and asked directly whether it was good and whether the findings were confirmed. Walking through it surfaced a serious one: a CRITICAL 9.8 "Http Request Smuggling" finding whose own evidence was nginx's stock `<h1>400 Bad Request</h1>` error page - the target correctly rejecting a malformed CL/TE request, not an attacker succeeding. The finding's own remediation text ("reject ambiguous requests with 400") describes exactly what the server had just done.

Traced it to `core/modules/smuggling_scanner.py`'s CL.TE probe: alongside its genuine, well-designed timing-based detection (does the server hang waiting for more body bytes - real evidence of a confused back-end), there was a second branch that treated ANY prompt 400 response containing generic phrases like "bad request" or "invalid request" as CRITICAL vulnerability evidence. Those phrases appear in literally every default nginx/Apache 400 error page regardless of why the request was rejected - the check had no way to distinguish "the server specifically detected a CL/TE conflict" from "the server rejects malformed requests in general," and treated a defensive rejection as if it were a confirmed exploit. The TE.CL and TE-obfuscation probes in the same module were already correctly designed (they only flag genuinely anomalous behavior) - this was isolated to the one branch.

Also explains why the report's overall Risk Score (9.8/10) was driven entirely by this one finding: `core/hunter.py` computes the headline score as `max(all individual CVSS scores)`, and `"http_request_smuggling"` carries a static 9.8/CRITICAL CVSS vector in the knowledge base (`core/knowledge.py`) applied uniformly regardless of how the finding was actually verified - a confirmed working desync and a defensively-rejected probe got the identical score.

Removed the flawed branch entirely - a fast, clean 400 now produces no finding (it's evidence against this vector, not for it). The timing-based hang detection is unchanged. Added 2 regression tests (`tests/api_scanners/test_smuggling_false_positive.py`) using a real raw-asyncio TCP server (matching how this module actually talks to targets - raw sockets, not aiohttp): one replicating the exact nginx 400 scenario from the report (must produce zero findings), one confirming a genuinely hanging back-end still produces a finding (the fix didn't remove real detection along with the false one).

### Report Accuracy — Five Fixes From an Independent Ground-Truth Review of a Real Scan Report

A user ran a full Hunt against their own site (waitlesshub.com), got a 31-finding report with a 9.8/10 risk score, then independently verified every finding against the site's actual code/DNS (not something I generated) and reported back which ones were real and which weren't. Two were things I'd already gotten wrong in my own earlier review of the same report: I had endorsed the Subdomain Takeover finding as trustworthy, and had missed that the GA4 finding was outright fabricated. Investigated every open item from that review, in order:

**Subdomain Takeover false positive.** `core/modules/subdomain_takeover.py`'s `_check_fingerprints()` flagged `takeover_risk: True` on `body_hit OR cname_hit` — meaning a subdomain's CNAME merely *pointing at* a cloud provider's domain (`cloudfront.net`, `s3.amazonaws.com`, `herokuapp.com`, ...) was sufficient on its own to declare an unclaimed-resource takeover, with no requirement that the live response actually show the provider's "nothing is claimed here" error page. Pointing at CloudFront/S3/Heroku is completely normal for a live, correctly-configured service — the report's `ftp.waitlesshub.com` finding fired for exactly this reason despite the subdomain resolving to the site's own production server the whole time. Fixed to require `cname_hit AND body_hit` — the CNAME now only narrows which fingerprint's body pattern to check, it's no longer sufficient by itself. 5 new regression tests (`tests/api_scanners/test_subdomain_takeover_false_positive.py`) confirm both the false-positive case (CloudFront CNAME + normal page → no finding) and that genuine unclaimed-resource signatures (NoSuchBucket, CloudFront's real rejection body) still fire correctly.

**GA4 Measurement ID — fabricated finding.** The user confirmed no GA4/gtag code exists on the page at all, yet the report claimed one. Traced to `core/templates/ga4-measurement-id.yaml`, part of the ~10,000-template nuclei-style scanner (`core/modules/template_scanner.py`) — its matcher checked for the bare substrings `"G-"` and `"UA-"` anywhere in the response body. `"G-"` doesn't get word-boundary protection in the matcher engine (it intentionally falls through to substring matching for prefixes like `"ORA-"` that need to prefix-match `"ORA-01017"`), so it coincidentally matches Bootstrap's ubiquitous `bg-*`/`g-*` utility classes (`class="row g-3"`, `class="bg-primary"`, ...) on any Bootstrap-based site with zero Analytics code. Reproduced empirically against a plain Bootstrap page with no tracking code — `_word_matches("G-", page)` returned `True`. Fixed by replacing the word matcher with a regex requiring the actual `gtag('config', 'G-XXXXXXXXXX')` call or a `googletagmanager.com/gtag/js?id=...`/`google-analytics.com/analytics.js?id=...` script inclusion, plus an `extract` block so a real match reports the actual measurement ID as evidence instead of just "found two characters."

**Apple/iOS/macOS/WebKit CVE templates matching a website.** The report showed 16 client-device kernel/browser-engine memory-corruption CVEs "confirmed" against an ordinary web target — vulnerabilities that by their nature require local exploitation on an Apple device and can never be verified via HTTP probing. Traced the mechanism (auto-generated NVD-bulk templates whose only universally-satisfiable req-def is a bare `status: 200` check) and found `_run_template()`'s existing skip-guard logic (added in earlier work this same session, before this specific report was reviewed) already handles this class correctly — empirically confirmed by running all 69 currently-active Apple/iOS/macOS/WebKit CVE templates against a synthetic ordinary homepage: zero produced a finding. Added a permanent regression suite (`tests/templates/test_template_false_positives.py`, 9 tests) covering both this and the GA4 fix via a real local aiohttp server, since neither had a test locking the behavior in before now.

**Account enumeration timing check — unreliable single-sample measurement.** `core/modules/auth_analyzer.py`'s `_check_account_enumeration()` timed exactly one request pair (one valid-looking email, one invalid-looking one) and flagged any ≥150ms gap as a timing-based leak. Ordinary network jitter — especially over a SOCKS5/Tor proxy, where per-circuit latency variance routinely exceeds 150ms on its own — can produce a gap that large from a single sample purely by chance; the user directly confirmed this by re-testing and finding no reproducible gap. Fixed to take 5 interleaved samples (only when status/body already look identical — a real status/body difference is already reliable signal on its own and doesn't need timing corroboration) and require both a real median gap **and** that the gap point the same direction in ≥80% of trials; random noise fails the consistency check even when an individual sample clears the threshold. Verified with a real local aiohttp server: a handler with pure jitter and zero real backend timing difference produces no finding, while a handler with a genuine, consistent ~280ms delay is still caught (`tests/auth_analyzer/test_account_enum_timing.py`).

**Report findings not sorted by severity.** The 31-finding technical report listed findings in raw scan-discovery order — a reader had to scan the whole numbered list to find the Critical/High findings instead of seeing them first. Added `_severity_sorted()` to `web/apps/reports/generators.py` and applied it everywhere the technical HTML/PDF report renders its findings table, plus to the executive-recommendations derivation (so recommendations are pulled from the most severe findings first, not whichever scanner phase happened to run first). 5 new tests in `tests/reports/test_severity_sorting.py`.

**"Git Exposure" finding mislabeled on an unrelated file.** The report showed a Critical "Git Exposure" finding pointing at `/sitemap.xml` — nothing to do with git. Root cause: `core/modules/git_exposure.py`'s findings never carried a `type` field of their own, so `core/hunter.py`'s `_normalise()` fell back to the fixed module-level source name (`"git_exposure"`) for *every* finding this module ever produces — an exposed `.env` file, a backup archive, an informational `package.json`, all labeled "Git Exposure" once the report generator turns `type` into a display title (`v.get('type','unknown').replace('_',' ').title()`). Fixed by having `_classify()` return a finding-specific `vtype` (`git_exposure`, `env_file_exposure`, `backup_exposure`, `config_file_exposure`, `private_key_exposure`, `htpasswd_exposure`, `shell_history_exposure`, `phpinfo_exposure`, `server_status_exposure`, `informational_file_exposure`) threaded through into each finding. Also removed `/robots.txt` and `/sitemap.xml` from the probed-path list entirely — both are intentionally public files fetched by every crawler and search engine by design, not a security finding under any interpretation. 5 new tests in `tests/git_exposure/test_finding_type_labeling.py` using a real local aiohttp server.

All 266 tests pass (`python -m pytest tests/ -q`). Deployed to `/opt/ds1hunter` (`core/modules/subdomain_takeover.py`, `core/templates/ga4-measurement-id.yaml`, `core/modules/auth_analyzer.py`, `web/apps/reports/generators.py`, `core/modules/git_exposure.py`) with timestamped backups, verified with `manage.py check` and a direct import/logic smoke-test against the deployed files before restarting `ds1hunter-api`; confirmed healthy post-restart (401 on an authenticated route, not a 404/500).

### Accuracy Improvements (8 False-Positive Fixes)

**LDAP Injection — confirmation tightened**
- Confirmation now requires LDAP-specific keywords in the response body in addition to HTTP 500. Generic server errors no longer produce a finding.

- Findings against known CDN, analytics, tracking, and social-media subdomains that are referenced by the target but not owned by it are suppressed before reporting.
